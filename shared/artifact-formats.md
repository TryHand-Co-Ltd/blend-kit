# BLEND Kit — artifact formats and template registry

Read [workflow](workflow.md) for discovery, authority, ownership and status. This registry is the single output-to-template mapping; do not maintain a parallel JSON/CSV source. All paths below are relative to the package root. Template versions are family-specific: topic `research@1.1.0`; all other current families `1.0.0`. Historical flat `research@1.0.0` remains a read-only legacy input, not the output template for new topics.

In source, package root is the directory containing `shared/` and `skills/`. A built self-contained skill must declare its emitted resource base and resolve this mapping to actually bundled assets (build-time relative-link/path rewrite is permitted). Do not interpret `skills/...` relative to a runtime workspace or leave it pointing to an absent source checkout. Asset bytes/family/version remain identical across profiles; build rewrites resource references, not business/format rules.

## Required template gate

Before authoring, resolve every requested filename/language to its row, read that exact asset, then follow required headings, field labels, order and conditional rules. Missing asset/mapping/version blocks that output. A sample document is not an implicit template. Do not generate optional files simply because templates exist. Copying historical/distribution files is preservation, not regeneration; unsupported DDL/language/output families require a separately approved template mapping.

Markdown templates and completed outputs retain `<!-- blend-template: FAMILY@VERSION -->` with the exact registry version as unobtrusive provenance; SQL uses `-- blend-template: sql-investigation@1.0.0`. Workbooks use exact `TemplateFamily` / `TemplateVersion` / `Language` properties: `test-report@2.0.0` for new workbooks. Remove template authoring instructions/placeholders from completed outputs. Metadata is not a claim of business approval. Review/template family evidence belongs in the existing evidence wrapper/Research, not an extra generated manifest.

Required/optional section labels below are exact level-2 headings, separated by `;` and preserved in listed order. Dynamic task/case/finding subsections are allowed under those headings. Localized field labels are fixed by the corresponding asset; the `Fields` column identifies their shared semantic schema. Templates must describe those fields and optional omission predicates explicitly. Required fields cannot be hidden by an otherwise correct heading. Bilingual counterparts have identical field/order/conditional semantics; their headings/prose differ only by language.

## Deterministic handoff gate

Use the shipped [artifact gate](scripts/artifact_gate.py) after saving final requested Markdown and before reporting BranchResult. Resolve the helper from this contract's directory, independently of the process cwd or application root. In source the registry resolves templates from the package containing `shared/` and `skills/`; in a self-contained skill it is `_kit/shared/artifact-formats.md`, and its rewritten `_kit/skills/...` paths resolve from that owning skill. Do not use a source checkout or test harness as a runtime dependency.

```text
python <resolved-artifact_gate.py> check --type implementation-plan --language ja --file <actual-saved-file> --filename plans/<scope>-implementation-plan.ja.md
python <resolved-artifact_gate.py> capture --root <verified-input-root> --file <selected-root-relative-file> --file <another-selected-root-relative-file>
```

Use the registered type/language/filename for each requested output; `--filename` is the registry-relative logical name, separate from the actual saved location. The check loads the exact mapped asset and enforces its family/version, H2 order, localized labels and filled slots. Follow **the asset's prescribed presentation**: an inline placeholder slot requires a nonempty concise summary on the label's own line; details may follow below. A prescribed block/list slot retains its populated bullets below. Keep labels and fixed headings exact, without parenthetical extensions. For example, planning source revisions and code-review verdicts need inline summaries; a following table alone cannot fill them. The fixed Inventory heading remains exact, and its table needs actual entries. Instructions, fenced examples and unfilled placeholders cannot satisfy fields.

A genuine scoped no-findings/no-open-questions/no-shared-fixtures result replaces only the template-authorized dynamic entries; do not invent a finding or fixture. Keep required sections with meaningful scoped none/reason for no DB or parallel impact. Conditional applicability, source obligations, per-entry completeness, bilingual meaning and approval remain separate review checks; this structural gate does not certify them. Historical inputs keep their original schema and bytes; run current-output conformance only on newly authored outputs. The Markdown gate does not certify XLSX/SQL: workbook identity/schema/revision/projection and render/recalculation remain the exporter/reviewer's separate checks.

Run the gate again after any final edits. Failed or unavailable checks keep the affected output Draft/Blocked and BranchResult incomplete; disclose the exact mismatch or missing capability. Never claim Complete or a clean template verdict from intended checks. Capture emits observed SHA256/size receipts to stdout only, reads raw file bytes and never creates a manifest, discovers extra inputs or implies approval. See [workflow capture/currentness](workflow.md#topic-research-currentness) for consumption and approval comparison.

For `test-report@2.0.0`, spreadsheet presentation is a deterministic projection rather than Markdown rendering. Strip one leading source list marker (`-`, `+`, `*` or `•`) before adding exactly one workbook bullet. Render Markdown inline code as `[identifier]`, preserving every character inside it (`**24` remains `[**24]`), and remove `**` only when it is emphasis outside code. Reject visible generated cells containing literal backticks, emphasis markers outside bracketed technical tokens or doubled bullet markers. Keep each status dropdown in one compact unmerged cell adjacent to its label; merge only the wider narrative fields. These invariants apply equally to JA and VI templates, generated reports and regression fixtures.

`<topic>` and `<scope>` are nonempty descriptive kebab-case basenames, never literal placeholders, separators, absolute paths, `.` or `..`. An exact verified Task ID may prefix the descriptive basename when needed; preserve its case/zeros and record source/parent metadata, do not infer or invent identity from a filename. Research/SQL patterns are feature-root-relative; plan patterns are feature-root-relative; code-review filenames follow the assigned docs/task owner.

`research@1.1.0` introduces required topic/purpose/dependencies/currentness semantics without changing the existing required H2 order; old `1.0.0` snapshots are consumed with their original schema and are never rewritten or repinned to satisfy new output conformance. SQL query fields are unchanged, so `sql-investigation@1.0.0` remains current.

For `implementation-plan` and `code-review`, registry presence alone does not establish emitted capability; matching assets and shipped resource closure must pass the inventory gate. Missing assets fail full inventory. Required H2 headings always remain; use a scoped none/no-candidates/no-impact statement when applicable, never empty sections. Corresponding assets define localized labels for every semantic field and H3 omission predicates.

`requested-review.*.md` represents a user-requested report basename, not a mandated new filename. Review in chat uses the same family without creating a file. `Language=neutral` applies only to SQL syntax/comment localization chosen for the audience. Registry row existence is planned capability until its asset is present; never claim complete-kit support from this table alone.

## Field and semantic invariants

- **Research:** topic/purpose/scope/questions, selected actual paths with per-file identities and decisive source/code/confirmation dependencies, currentness/gaps; source identity/authority/revision and actual code/content baseline; clause → action → desired/preserved outcome → As-Is anchor → impact/owner → gap/proof → recipient. Record discovered facts, advice and business decisions separately. No raw call-graph dumps or inferred approval.
- **Split Task:** outcome title, Main Screen, Affected Screens bullets (or verified non-UI seam), bounded scope, business changes, short Technical with verified repo-relative anchors/roles, start/integration dependencies and concise completion outcome. Numbering is local, not a fabricated source Task ID.
- **AC:** stable IDs in business-flow/outcome groups and unchecked checklists; actor/condition/outcome/exceptions/preserved state/source-backed basis. Do not convert steps/technical file plans into AC or merge independently failing outcomes until failure is hidden.
- **Business Q&A:** scenario → unresolved decision/impact → marked proposal/options → independently answerable question. Preserve leaf status; a sibling answer never resolves all leaves. No-open-questions result states the assessed scope, not invented questions.
- **Database Design:** storage unit, As-Is/To-Be, columns/type/NULL/default, identity/relationships/constraints, validation/save/readback/lifecycle and compatibility/verification. State proposal authority where needed. Index rationale, transaction/concurrency or copy/import/migration details apply only to affected obligations. No arbitrary new tables/enums/rounding/locks from examples.
- **SQL draft:** concrete question, source/schema basis, safe parameters and read-only investigation query; distinguish unexecuted query from observed data. Missing schema detail remains explicit; never embed credentials/private values.
- **Scope and approach:** source/baseline/research basis, roles/environment, justified in/out scope, preparation/run selection, entry/exit/evidence, clause/branch → case/variant or classified gap. Preserve obligations with unknown oracle or unavailable fixture; don't count them as absent scope.
- **Case:** stable ID/title; feature → operation/function; source/priority/expected basis/readiness; separate configuration/trigger/observation locations or genuine API/job/static seam; actor/permission, entity/state/fixture and discriminating values; ordered action/expected/preserved state; mandatory variant identity, proof/reset when relevant. Explicit shared-context reference may avoid repeated prose; per-case overrides must resolve uniquely. No hidden previous-case state chain or empty actual-result section in design Markdown.
- **Variants:** one design case with named, independently reportable parameter rows when setup/action/oracle are equivalent. Distinct permission/state/lifecycle assertions need separate cases or clear variants; no dropped branch to reduce file length. Group main path → variants/boundaries → validation/permission → errors/recovery. Priority is for run selection, not regrouping all High cases together.
- **Fixtures:** stable reference, role/school/year/owner/state where relevant, decisive input/expected values and target/non-target separation; reproducible create/verify/reset with source-supported actions. Missing preparation remains a readiness gap. No real personal or secret values.
- **Review:** complete assigned inventory, source/code/template comparison, findings with actionable updates and justified valid equivalents; each proposal says what/where/why/preserved outcome/how to verify. Re-review retains stable IDs/closure evidence. Different template labels are a conformance issue only when required structure actually violated; prose differences alone are not semantic defects.

- **Implementation plan:** textual PlanningBasis separates current authority, review disposition and exact revision/scope approval; outcome steps/prerequisites/ownership/contracts, AC-to-step-to-proof mapping, preservation, conditional parallel/DB/migration risks and final validation. Commands are portable from verified toolchain, proof Planned/Not run; output Draft for review, execution permission separate.
- **Code review:** textual ReviewBasis pins actual base/head/working identities and intended/actual/inspected/excluded scopes; complete assigned inspection plus bounded consumer risk. Findings use independent scope/origin/severity/confidence/completion effects and common inline RoleDisposition. Acceptance/regression/standards/DB and runtime/QA/release proof remain separate; partial scope or missing required roles is not clean.

## Unified test report

`test-report@2.0.0` has exactly two localized sheets: Overview and full Testcases blocks. The registered JA/VI block assets are the active layout. Source assets contain one explicitly labeled placeholder block so humans can inspect the layout; generation deletes it before source projection, and generated reports contain no sample/placeholder values. Each real block has complete ID/title, status on the next row, screen/function beside screen_relative_path and four sections: test conditions, ordered actions, expected and actual/image area. Titles and technical labels are bold; step numbers are bold while action sentences remain normal. Values use concise bullets and Vietnamese display text starts sentence case. Reset is the last action. Each variant has one actual/status/image slot; single-variant header status is editable, multi-variant header status derived. No visible link/caption/footer/backlink rows, hidden dataset or third image sheet.

New case design uses test-cases@1.1.0 with a verified relative screen URL, unknown or verified non-UI not-applicable. Frozen 1.0.0 case inputs remain readable with visible unknown paths. Scope/data remain 1.0.0. Preserve IDs, authority/readiness, obligations and decisive literal values.

Overview separates case/variant totals and preparation/execution. Only Confirmed + Ready PASS/FAIL with nonempty actual are counted; zero denominator is no data, PASS+SKIPPED incomplete. Unknown expected/preparation cannot become requirement PASS. Actual/image/run metadata starts blank and status NOT RUN. Non-PASS reason and next action belong in actual.

Generator refuses existing paths. Checker reads the matching saved XLSX without repair, checking source/formulas/navigation/merges, observations, privacy and image bindings. Complete requires genuine closure/access/image review and verified routes. Native Google Sheets checks are independent and unavailable from the XLSX checker. No invented evidence, upload/share or application execution follows.

Historical families/bytes/results/distributions remain historical; do not relabel them. Authorized migration retains the earlier report with its matching source/runtime.

## Validation boundary

The `customer-report` fixture dispatcher name is retained for historical scenario identity; its active checks cover the unified same-file lifecycle, not a second output operation.

`python tests/test_kit.py --area templates|topics|task|test-spec|review|planning|code-review|customer-report|package|all` dispatches each requested fixture branch's `checks.py:run(root: pathlib.Path)`. Checks raise on failure and return observations; missing branches are unavailable, never Passing. Focused template controls can pass while later assets are Planned, explicitly naming that limit. `--area all` additionally requires every registry asset and matching identity metadata; incomplete inventory fails the final package gate. Semantic runtime scoring on Codex/Cursor/Claude, bilingual content judgment and workbook render/recalculation remain independent required proof. Test/schema success never stands in for them.
